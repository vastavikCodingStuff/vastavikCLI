# Agent Development & Release Governance — VastavikCLI / VASTAVIK CLI

> **MANDATORY for every AI agent, human contributor, and automation working in this repository.**
> This file defines the single source of truth for CI/CD, Git standards, change classification, and release flows.
> No agent may bypass, shortcut, or reinterpret the rules below.

---

## 1. Context & Purpose

This repository adheres to **strict automated CI/CD and Git standards**. All terminal, PRoot/Debian, and Jetpack Compose work must be reproducible, verifiable, and traceable on GitHub with **no "Unverified" badges**.

Whenever an agent performs **any** task in this repository, it must:

1. **Classify** the task as either:
   - **Minor Patch / Small Change** — documentation, bug fixes, UI tweaks, chore
   - **Major Feature / Big Change** — new subsystems, distro hub upgrades, PTY/service core modules, breaking changes
2. **Strictly follow the lifecycle rules** documented in **Section C** for that classification.
3. **Never commit directly to `main`** and **never produce unverified commits**.

Failure to follow this document is a workflow violation — fix the workflow before continuing the task.

## 2. General Development Standards

### A. Architecture & Environment

- **Architecture Target: Exclusive Android ARM64 (`arm64-v8a` / `aarch64`).**
  - Strictly no `x86`, `x86_64`, `armeabi-v7a`.
  - `app/build.gradle.kts` must contain:
    ```kotlin
    ndk { abiFilters += listOf("arm64-v8a") }
    ```
  - Release artifact must be verified as `arm64-v8a` only (see `apkanalyzer` / `unzip -l` check in Mode 2).
  - All native binaries (`assets/bin/arm64-v8a/proot`, `libVASTAVIK CLI-pty.so`) are `aarch64` statically compiled.

- **Environment: Kotlin, Jetpack Compose, PRoot/Debian native toolchain.**
  - Language: Kotlin `1.9+`, `jvmTarget 17`
  - UI: Jetpack Compose + Material3 (`compose-bom`, `activity-compose`)
  - Terminal: `PtyProcess` (JNI `openpty`/`fork`/`exec`) with `ProcessBuilder` fallback, `TerminalSession`/`SessionManager`
  - Subsystem: Minimal Debian ARM64 rootfs (`debian` + `distros/<id>`) with `apt`/`dpkg`/`coreutils`/`bash`/`glibc`; DNS seeded via `etc/resolv.conf` (`1.1.1.1`, `8.8.8.8`)
  - Shared binaries: `$FILES_DIR/bin/proot`; isolated distros: `$FILES_DIR/distros/<distro_id>`; cache: `$FILES_DIR/downloads/`

- **Pre-commit Checks (Required before ANY PR):**
  - Code must compile cleanly:
    ```bash
    ./gradlew assembleDebug
    # or
    ./gradlew test
    ```
  - No PR may be opened with compile errors, lint failures, or missing `arm64-v8a` filters.
  - For Compose changes, verify `./gradlew assembleDebug` succeeds locally; for native changes, also verify `libVASTAVIK CLI-pty.so` builds for `arm64-v8a`.

### B. Git & GitHub Verification Protocol (Mandatory for ALL changes)

#### 1. Branching Model

- **Never commit directly to `main`.**
- Always create a **descriptive working branch** from up-to-date `main`:
  - Small updates: `fix/short-description` or `chore/short-description`
    - e.g., `fix/extra-keys-ctrl-latch`, `chore/update-readme-debian`
  - Big updates: `feature/feature-name`
    - e.g., `feature/dual-drawer-distro-hub`, `feature/arm64-distro-manager`
- Branch creation:
  ```bash
  git checkout main
  git pull origin main
  git checkout -b fix/short-description   # or feature/feature-name
  ```

#### 2. Verified Commits (No "Unverified" Badges on GitHub)

- **All commits must be cryptographically signed** using GPG or SSH (`git commit -S -m "..."`), **or** committed via authenticated GitHub API/CLI (`gh`) sessions linked to a verified key.
  - GPG/SSH:
    ```bash
    git commit -S -m "fix: correct CTRL latch handling"
    # or
    git commit -S -m "chore: update Debian resolv.conf seeding"
    ```
  - Verified key must be registered to the GitHub account: `Settings → SSH and GPG keys → Verified`.
- **Author email must match the verified GitHub account email.**
  ```bash
  git config user.email "verified-email@example.com"
  git config user.name "Verified Name"
  git log --show-signature -1   # must show Good signature
  ```
- Commits pushed with an unverified email or without `-S` **must be rejected** — amend with correct identity and re-push:
  ```bash
  git commit --amend --reset-author -S
  git push --force-with-lease
  ```

#### 3. Pull Request Protocol

- Push branch and create a PR to `main` via `gh` with a **formatted markdown summary**:
  ```bash
  git push -u origin fix/short-description
  gh pr create --title "fix: short description" --body "## Summary
  - ...
  ## Changes
  - ...
  ## Verification
  - [x] ./gradlew assembleDebug passed
  - [x] Commit signed (verified)
  "
  ```
- **Wait for checks and verification** before merge:
  ```bash
  gh pr view --json statusCheckRollup,commits
  # statusCheckRollup[].state must be SUCCESS
  # commits[].signatureState must be VERIFIED (no UNVERIFIED)
  ```
- Do not merge if any check is `FAILURE`/`PENDING` or any commit is `UNVERIFIED`.

#### 4. Merge, Squash & Clean

- The PR **must be merged using the Squash and Merge strategy**:
  ```bash
  gh pr merge <PR_NUMBER> --squash --delete-branch
  ```
  - Squash preserves a single verifiable commit on `main` with the PR title as the squashed message.
  - `--delete-branch` removes the remote feature branch automatically.
- **Automatically delete the local and remote feature branch post-merge:**
  ```bash
  git branch -d fix/short-description          # local
  git push origin --delete fix/short-description  # remote if not already deleted
  ```
- **Switch back to `main` and pull the latest squashed commit:**
  ```bash
  git checkout main
  git pull origin main
  ```
- **Prune tracking branches:**
  ```bash
  git fetch --prune
  ```

### C. Change Classification & Execution Pipelines

Classify every task **before** writing code. Use the smallest applicable mode — never downgrade a Big Change to Small.

#### Mode 1: Small Change Workflow (Documentation, Bug Fixes, UI Tweaks)

Use for: README, comments, `ExtraKeysBar` styling, divider colors, `resolv.conf` tuning, string fixes, non-breaking UI polish.

1. **Branch from up-to-date `main`:**
   ```bash
   git checkout main && git pull origin main
   git checkout -b fix/short-description   # or chore/short-description
   ```
2. **Apply changes and verify compilation locally:**
   ```bash
   ./gradlew assembleDebug
   # or
   ./gradlew test
   ```
3. **Commit with signature:**
   ```bash
   git add -A
   git commit -S -m "chore/fix: <concise imperative description>"
   ```
4. **Push and create PR using `gh pr create`:**
   ```bash
   git push -u origin fix/short-description
   gh pr create --title "fix: ..." --body "## Summary ..."
   ```
5. **Verify commit signature status:**
   ```bash
   gh pr view --json statusCheckRollup,commits
   git log --show-signature -1
   ```
6. **Squash-merge via `gh pr merge --squash --delete-branch`:**
   ```bash
   gh pr merge <PR_NUMBER> --squash --delete-branch
   ```
7. **Return to `main`, prune local tracking branches:**
   ```bash
   git checkout main
   git pull origin main
   git fetch --prune
   git branch -d fix/short-description  # if not already deleted
   ```

#### Mode 2: Big Change Workflow (Major Features, Subsystem Upgrades, Core Modules)

Use for: `DualDrawerScaffold`, `SessionManager`/`SessionState`, `PtyProcess`/`TerminalSession` rework, `PRoot` upgrade, `DistroHub`/`DistroDownloader` catalog, `TerminalSessionService` lifecycle changes, any `app/build.gradle.kts` ABI or `minSdk`/`targetSdk` bump.

1. **Execute steps 1 through 6 from Mode 1** (Branch → Signed Commit → PR → Verify → Squash & Merge → Delete Feature Branch):
   ```bash
   git checkout -b feature/feature-name
   # ... implement ...
   ./gradlew assembleDebug
   git commit -S -m "feat: add dual-drawer distro hub"
   git push -u origin feature/feature-name
   gh pr create --title "feat: add dual-drawer distro hub" --body "..."
   gh pr view --json statusCheckRollup,commits
   gh pr merge <PR_NUMBER> --squash --delete-branch
   git checkout main && git pull origin main && git fetch --prune
   ```
2. **Once merged onto `main`:**
   - **Determine the next semantic version tag** (e.g., `v1.2.0`) following SemVer:
     - `MAJOR.MINOR.PATCH`
     - `MAJOR` for breaking PRoot/ABI changes, `MINOR` for features, `PATCH` for fixes
     - Inspect last tag: `git describe --tags --abbrev=0` then bump appropriately.
   - **Bump version code and version name in `app/build.gradle.kts`:**
     ```kotlin
     defaultConfig {
         versionCode = <incremented integer>
         versionName = "<x.y.z>"
     }
     ```
     Commit the bump via the same **Mode 1** signed-PR flow, or include it in the squashed feature if still on branch.

3. **Compile ARM64 APK — Execute Gradle release build targeting ARM64:**
   ```bash
   ./gradlew assembleRelease
   # Target output: app/build/outputs/apk/release/app-arm64-v8a-release.apk
   ```
   - **Verify the generated artifact is strictly built for `arm64-v8a`:**
     ```bash
     unzip -l app/build/outputs/apk/release/app-arm64-v8a-release.apk | grep -E "lib/|arm64"
     # must show only lib/arm64-v8a/libVASTAVIK CLI-pty.so, no lib/x86, lib/armeabi-v7a
     apkanalyzer apk summary app/build/outputs/apk/release/app-arm64-v8a-release.apk
     ```
   - If the APK contains any non-`arm64-v8a` native libs, fail the release.

4. **Create GitHub Release & Upload Asset — Use GitHub CLI (`gh release create`) to tag `main` and attach the compiled APK:**
   ```bash
   gh release create v<VERSION> \
     app/build/outputs/apk/release/app-arm64-v8a-release.apk#Vastavik-Terminal-v<VERSION>-arm64.apk \
     --title "Release v<VERSION>" \
     --notes-file RELEASE_NOTES.md
   ```
   - Tag must be `v<VERSION>` (e.g., `v1.2.0`) on the squashed `main` commit.
   - Asset name must be `Vastavik-Terminal-v<VERSION>-arm64.apk` (rename via `#` suffix).
   - `RELEASE_NOTES.md` must contain the exact structure below.

5. **Formatted Release Notes Structure — The release notes must follow this exact markdown format:**
   ```markdown
   ## What's Changed in v<VERSION>
   - 🚀 **New Features**: Summary of features added.
   - 🛠️ **Improvements**: Performance, PRoot, or UI enhancements.
   - 🐛 **Bug Fixes**: Issues resolved in this cycle.

   ### Architecture & Compatibility
   - **Target**: Android ARM64-v8a (64-bit only)
   - **Subsystem**: Minimal Debian ARM64 rootfs with `apt`
   - **Commit SHA**: <squashed commit SHA on main>
   ```

   - Replace `<VERSION>` with the new version (e.g., `1.2.0`).
   - Replace `<squashed commit SHA on main>` with the full SHA from `git rev-parse HEAD` after `git pull origin main`.
   - Example:
     ```markdown
     ## What's Changed in v1.2.0
     - 🚀 **New Features**: Dual-drawer navigation and ARM64 Distro Hub with 6 isolated rootfs.
     - 🛠️ **Improvements**: PTY resize via TIOCSWINSZ, obsidian ExtraKeys bar latching.
     - 🐛 **Bug Fixes**: resolv.conf race on concurrent extracts.

     ### Architecture & Compatibility
     - **Target**: Android ARM64-v8a (64-bit only)
     - **Subsystem**: Minimal Debian ARM64 rootfs with `apt`
     - **Commit SHA**: a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0
     ```

## 3. Enforcement & Compliance

- Any agent that opens a PR without `./gradlew assembleDebug` passing **must** close the PR and fix compilation first.
- Any `UNVERIFIED` commit badge is a hard blocker — re-sign and force-push with `--force-with-lease`.
- Direct pushes to `main` are prohibited; only `gh pr merge --squash` may mutate `main`.
- Big Changes without an `arm64-v8a`-only verified APK and a properly formatted `gh release create` are incomplete.
- Store `RELEASE_NOTES.md` in the repo root for auditability before running `gh release create`.
